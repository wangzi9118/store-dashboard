# 门店财务运营看板 v1.0

一套面向多门店经营场景的财务数据管理系统。系统支持 Excel 账目导入、月度手工录入、经营看板、门店 PK、用户权限和跨设备共享数据。

本文档同时面向两类读者：

- 使用者：了解如何登录、录入数据、导入 Excel 和查看看板。
- 开发者或 AI：了解代码结构、数据模型、权限边界和不可破坏的业务规则。

## 当前功能

### 数据看板

- 默认进入当前年份的“全部”视图。
- 展示八项指标：营业额实收、总支出、总提现、订货支出、订货占比、工资支出、工资占比、毛利率。
- 全年视图显示月度折线图，并与上一年度全年数据进行同比。
- 月份视图不显示折线图，与上一个月进行环比；1 月与上一年度 12 月比较。
- 收支渠道和收支明细支持展开、折叠。
- 金额为 0 的收支渠道不在看板中显示。
- 收支明细按收入、支出两列显示，并分别计算明细合计。

### 月度录入

- 选择门店、年份和月份录入数据。
- 可以新增、修改和删除收入渠道、支出渠道。
- 可以新增、修改和删除收支明细。
- 可以填写订货支出、工资支出和总提现。
- 营业额实收和总支出由渠道金额自动计算，不能直接修改。
- 收支明细独立保存，不参与营业额、总支出或利润率计算。
- 支持导入 `.xls` 和 `.xlsx` 文件，单个文件最大 15 MB。

### 门店 PK

- 选择两个不同门店进行对比。
- 支持全年或具体月份比较。
- 展示双方具体数值和 `A - B` 差值。
- 支持切换指标查看全年趋势图。
- 观察者只能选择自己获准查看的门店。
- 可见门店少于两家时，页面会提示无法进行双门店对比。

### 门店管理

- 新增、重命名和删除门店。
- 删除门店时，同时删除该门店的月度记录和年度目标。
- 仅管理员可以使用。

### 用户和权限管理

- 创建、删除观察者账号。
- 修改管理员或观察者密码。
- 查看每个账号上一次成功登录的时间；从未登录的账号会明确标识。
- 使用下拉多选框设置观察者可以查看的门店。
- 支持一键选择“全部门店”。
- 管理员始终可以查看和管理全部门店。

## 用户角色

| 功能 | 管理员 | 观察者 |
| --- | --- | --- |
| 数据看板 | 全部门店 | 仅授权门店 |
| 门店 PK | 全部门店 | 仅授权门店 |
| 月度录入和 Excel 导入 | 可以 | 不可以 |
| 门店管理 | 可以 | 不可以 |
| 用户和权限管理 | 可以 | 不可以 |
| 修改业务数据 | 可以 | 不可以 |

权限不仅由前端菜单控制，服务端接口也会校验角色：观察者向数据写入接口发送请求会收到 `403`。

## 初始管理员

数据库第一次启动时会自动创建以下管理员：

| 项目 | 值 |
| --- | --- |
| 账号 | `wyb` |
| 初始密码 | `123456` |
| 角色 | 管理员 |

登录后可在“权限管理”中修改管理员密码。密码经过 `scrypt` 加盐哈希后存入数据库，不保存明文。

> 说明：如果数据库中已经存在 `wyb`，重启服务不会把其密码重置为 `123456`。

## 数据计算规则

这些规则是系统的核心业务约束：

```text
营业额实收 = 所有收入渠道金额之和
总支出     = 所有支出渠道金额之和
订货占比   = 订货支出 / 营业额实收
工资占比   = 工资支出 / 营业额实收
毛利率     = (营业额实收 - 总支出) / 营业额实收
```

当营业额实收小于或等于 0 时，订货占比、工资占比和毛利率均按 0 处理。

收支明细只用于记录和阅读，不参与上述任何计算。修改明细不会改变营业额实收、总支出或利润率；只有修改收支渠道金额才会改变这些指标。

## Excel 导入规则

系统寻找包含“店、月、营业额”表头的工作表作为汇总页，并尝试识别明细工作表。

### 汇总页

- 门店名称和月份用于定位月度记录。
- 营业额实收实际以识别到的收入渠道合计为准。
- 总支出实际以识别到的支出渠道合计为准。
- `订货总支出`写入订货支出。
- `工资`写入工资支出。
- `提现`或`提取`列存在时写入总提现。
- 渠道中正数归入收入，负数归入支出，支出金额以绝对值保存。
- `总支出`、`支出合计`等汇总列不会再次作为渠道导入，避免重复计算。
- 全部为空或全部为 0 的月份会被忽略。
- Excel 中出现系统尚不存在的门店时，会自动创建门店。

### 明细页

- 识别月份、日期、明细或摘要、收入、支出列。
- 导入内容写入对应月份的收入明细和支出明细。
- 明细不会参与经营指标计算。
- 重新导入同一月份时，会替换此前由 Excel 导入的渠道和明细，同时保留手工新增内容。

导入前页面会提供预览，用户确认后才会正式更新系统数据。

## 本地开发

### 环境要求

- Node.js 22.5 或更高版本，推荐 Node.js 24。
- npm。

项目使用 Node 内置的 `node:sqlite`，不需要额外安装 SQLite 服务或数据库软件。

### 安装依赖

```bash
npm install
```

### 启动开发环境

开发时需要同时运行后端和前端。打开两个终端：

终端 1，启动后端和 SQLite 数据服务：

```bash
npm run server
```

终端 2，启动前端开发服务：

```bash
npm run dev
```

默认地址：

- 前端：`http://127.0.0.1:5173/`
- 后端：`http://127.0.0.1:5174/`

Vite 会把 `/api` 请求代理到 `http://127.0.0.1:5174`。

### 常用命令

```bash
npm run dev       # 前端开发服务
npm run server    # 后端和 SQLite 服务
npm run build     # TypeScript 检查并构建生产文件
npm run lint      # 静态代码检查
npm start         # 生产模式启动，提供 dist 页面和 API
npm run preview   # 预览已经构建的前端文件
```

## 生产部署

```bash
npm install
npm run build
npm start
```

生产模式下，`server.mjs` 默认监听 `0.0.0.0:5174`，同时提供前端静态页面和 API。可使用环境变量调整：

```bash
HOST=127.0.0.1 PORT=5174 npm start
```

建议：

- 使用 PM2 或 systemd 保持 Node 服务运行。
- 使用 Nginx 或 Caddy 配置域名、HTTPS 和反向代理。
- 公网部署必须使用 HTTPS，避免登录信息被明文传输。
- 持久化并定期备份 `data/` 目录。
- 升级程序时不要覆盖或删除现有数据库。

更具体的说明见 [`DEPLOY.md`](./DEPLOY.md)。

## 数据保存方式

主数据库文件：

```text
data/store-dashboard.sqlite
```

SQLite 中包含以下表：

| 表 | 用途 |
| --- | --- |
| `app_state` | 保存完整业务数据 JSON，包括门店、月度记录和年度目标 |
| `users` | 保存用户、密码哈希、角色和上次登录时间 |
| `observer_store_permissions` | 保存观察者与可查看门店之间的关系 |
| `sessions` | 保存登录会话的令牌哈希和过期时间 |

当前业务数据采用单条 `app_state` JSON 保存，适合轻量服务器和小规模团队。多位管理员同时编辑时采用最后一次写入结果，因此不适合高并发协同录入。

浏览器 `localStorage` 只用于管理员的本地缓存、旧数据迁移和服务暂时不可用时的降级。观察者不会使用本地缓存替代服务端授权数据，避免显示未授权门店。

## 登录和会话

- 登录成功后，服务端设置 `HttpOnly`、`SameSite=Lax` 的会话 Cookie。
- 会话默认有效期为 7 天。
- 前端通过 `GET /api/auth/me` 恢复登录状态。
- 退出登录会删除当前会话，不会删除业务数据。
- 观察者读取 `/api/data` 时，服务端会过滤门店、月度记录和年度目标。
- 只有管理员可以写入 `/api/data`。

## 核心数据模型

`AppData` 是业务数据根对象：

```ts
interface AppData {
  stores: Store[]
  records: MonthlyRecord[]
  targets: AnnualTarget[]
  seeded: boolean
}
```

每个 `MonthlyRecord` 由 `storeId + year + month` 唯一定位，主要包含：

- `incomeChannels`：收入渠道，合计生成 `sales`。
- `expenseChannels`：支出渠道，合计生成 `totalExpense`。
- `orderExpense`：订货支出。
- `payroll`：工资支出。
- `withdraw`：提现。
- `incomeItems` / `expenseItems`：独立收支明细，不参与经营指标计算。

保存月度数据时必须经过 `syncRecordTotals()`，保证 `sales` 和 `totalExpense` 与渠道合计一致。

## AI 和开发者维护约束

修改代码前应先阅读相关页面、`src/types.ts`、`DataContext.tsx` 和对应 `src/lib` 模块。必须保持以下规则：

1. 不要把营业额实收和总支出改回可手工输入字段；它们必须来自渠道合计。
2. 不要让收支明细参与 KPI、利润率、渠道合计或门店 PK 计算。
3. Excel 的负数渠道属于支出，但总支出等汇总列必须排除，避免重复。
4. Excel 全空或全 0 月份必须忽略。
5. 重新导入 Excel 时，保留手工渠道和手工明细，仅替换 Excel 来源的数据。
6. 观察者权限必须在服务端执行，不能只隐藏前端菜单。
7. 观察者不能读取未授权门店，也不能写入业务数据。
8. 管理员路由需要同时保留前端路由保护和服务端接口校验。
9. 修改用户或权限功能时，不得把密码明文保存到数据库或浏览器。
10. 删除门店时，要同步删除其月度记录和年度目标。
11. 看板全年视图使用同比，月份视图使用环比；折线图只在全年视图显示。
12. 不要重新加入总分红、净利率或旧版 Excel 经营概览模块。

完成代码修改后，至少执行：

```bash
npm run build
npm run lint
node --check server.mjs
```

涉及权限、认证或数据过滤时，还应验证：未登录返回 `401`、观察者写入返回 `403`、观察者只收到授权门店、管理员可以正常读写。

## 已知限制

- 年份标签当前固定为 2024 至 2030。
- 业务数据整体写入单条 JSON，不支持数据库级的逐记录并发冲突处理。
- 没有“忘记密码”流程；管理员密码遗失时需要直接维护数据库或增加恢复工具。
- 会话表目前没有定时清理过期记录。
- 管理员初始账号由代码初始化，公网部署后应立即修改初始密码。
